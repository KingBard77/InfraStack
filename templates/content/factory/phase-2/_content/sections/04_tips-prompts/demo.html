Prompt Tips

The generator works best when the prompt names the important __DOMAIN__ decisions directly. Write for the parser and the reviewer, not for a marketing brief.

What should the prompt include?

Good prompts name the technical intent directly before listing optional detail.

  • Name the scope, environment, region, zone count, or placement model when those values matter.
  • Describe the main entry path, internal tiers, protected components, and private access choices.
  • Call out observability, logging, routing, security controls, and dependency boundaries explicitly.
  • State negative choices directly when they matter, such as no public entry, no database tier, or private only.
What prompt habits produce cleaner diagrams?

Clean prompts isolate one scenario and use exact domain terms the parser can map consistently.

  • Keep one environment or scenario per prompt.
  • Prefer exact domain terms over broad phrases such as secure backend or high availability.
  • Use a preset for a stable baseline, then refine the generated model with controls and the inspector.
  • Separate design intent from implementation detail when the workspace only models the higher-level view.
What needs explicit review after generation?

Generated output still needs human review where assumptions, risk, and unsupported details matter.

  • Assumptions created from short or ambiguous prompts.
  • Security-sensitive, regulated, hybrid, or shared-service patterns.
  • Exact routing, identity, encryption, backup, retention, sizing, cost, and operations decisions.
  • Any service, dependency, or constraint that is outside the workspace model.
